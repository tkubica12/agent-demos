Deployed topology

The reference deployment runs two Workers, hermes and hermes2, in one resource group. Sandbox Groups, Foundry, and monitoring run in Sweden Central; Service Bus, Container Registry, and the workload VNet run in North Europe.

The dependency base pins Hermes 0.22.6. Source releases, compute identity, and channel registration are independent. Each Worker also has a native managed receiver resource; it is not another always-on Sandbox.

Identity and access

Each Sandbox Group keeps its user-assigned identity. A separate native receiver resource has a system identity. Azure integrations use Entra; existing operator and runtime-local API credentials remain application boundaries. No registry key, SAS connection string, or new application secret is introduced.

Only the heavy runtime dependency image uses ACR native-v2 conversion and runtime-group AcrPull. Gateway and MCP services convert a public Python digest directly. No registry token or admin credential exists. Prepared group-scoped images are reused.

The dependency base pins official Hermes 0.22.6 and contains LibreOffice, compiled .NET helpers, Node packages, and sealed-environment dependencies. Application source is not baked into that image. Thin-service requirements come from frozen locks; approved-feed wheels are downloaded during preparation and installed offline into a lock-addressed environment. A later source change reuses it without pip or image build.

Before touching runtime compute, gateway maintenance rejects new admissions and checks unfinished work. Actual native task/executor counters protect the runtime source switch. Completed or quarantined receipts can await settlement without repeating effects. A base-image or compute replacement may still change a native URL and require endpoint reconciliation. Superseded services remain tracked until the replacement passes real checks.

Native home archives and checked SQLite journal backups use platform-managed Blob volumes. SQLite snapshots and publication locks stay on local disk; only copied, renamed checkpoints reach Blob. Unknown channel effects are retained in the journal and dead-lettered, never reported as delivered. Deleting a Sandbox Group deletes its volumes.

Memory suspend is not disaster recovery, and stopped CPU/RAM is not a zero bill: Service Bus, ACR, storage, and monitoring retain independent charges. Managed source polling can delay scheduled work; it is not on the interactive Teams path. The rejected three-hop design took 161-175 seconds despite 4-13 seconds of model work. Normal chat now starts immediately and uses native Runs directly. Fast reply, scheduled-message settlement, and process retention are measured separately.

Observability

Application Insights receives metadata-only OpenTelemetry spans. Worker and session attribution connect the gateway request, runtime invocation, model calls, and tools. Prompts, responses, bearer tokens, and tool payloads do not belong in this trace stream.

The Foundry external-agent registration links this execution to its monitoring surface. Registration does not move the agent into Foundry hosting or establish evaluation quality.

The Sandbox-origin egress path preserves TraceId but can rewrite ParentId; its intermediate platform span is not available in application telemetry. Correlation is therefore useful without a complete platform-hop tree. The native /v1/responses path also lacks explicit session correlation.

An interrupted native handoff retains its lease to prevent misattributing later spans. Restart the affected wrapper/native runtime processes before reuse; do not fabricate a parent span or silently clear the fence.

Production hardening

This is a target design, not the deployed state. Service Bus moves to Premium, and Service Bus and Foundry get private endpoints in the workload VNet. A peered enterprise hub provides DNS, firewall, controlled egress, and routes to existing private MCP services and backend APIs.

Tools fit three patterns: Microsoft-hosted MCP services on public HTTPS, existing MCP services in the customer network, or a custom MCP adapter deployed with the solution. Identity checks stay the same in every pattern.

Keep infrastructure declarative, source releases reproducible, native admissions durable, and every identity and recovery boundary explicit.

Component reference

Agent 365

Entra and Microsoft 365 objects

Each Worker has an agent blueprint, an Agent Identity, and a licensed Agent User. Scripts create them and register the messaging endpoint as the gateway URL plus /api/messages. Terraform does not manage these objects.

Teams and Microsoft 365

User-facing workloads

Users mention the Agent User in Teams, mail it, or comment in Office documents. Work IQ and Graph calls from the runtime run as the Agent User.

Gateway Sandbox Group

Memory suspend after 300 s

The bridge validates Agent 365 Activity Protocol authentication and handles Teams turns directly through native Runs over OnDemand HTTPS. Interactive messages are not persisted to a recovery queue. Its managed identity owns the scheduling connection and generated-app lifecycle; it cannot provision runtime compute. The journal is checkpointed to the gateway-state Blob volume for scheduling receipts and bounded conversation state.

Agent runtime Sandbox Group

Hermes 0.22.6 / 300-second Memory threshold

A dependency image and separately hashed source release host one native writer. Model requests use native Runs over authenticated OnDemand HTTPS; there is no runtime queue consumer or custom transport journal. Native home archives use the hermes-backups Blob volume. Actual native task/executor counters protect updates. Its VNet connection reaches private MCP; source changes need not replace compute.

Generated apps Sandbox Group

One Sandbox per app

The gateway starts each Worker-created app in its own Sandbox with Entra-protected ports. Apps suspend after 5 idle minutes and expire after a lifetime of 24 hours by default (15 minutes to 7 days).

Public shipments MCP

Public HTTPS / Memory after 300 s

A public Python base plus verified source release serves demo shipments. Entra enforces tenant, issuer, audience, and approved shipment scope/application role. The native port is OnDemand; no registry grant is needed.

Private incidents MCP

Private ingress / Memory after 300 s

The group remains irreversibly linked to the Express environment. Application authorization pins the expected Worker Agent Identity and incident role. Its public Python base and source release need no ACR image.

Service Bus and native receivers

Standard / Entra / scheduling queue only

Each Worker has one queue for enabled cron, Dreaming, and deterministic publication retries, with a fourteen-day TTL. No activity-recovery queue exists. Locks are five minutes; duplicate detection is one hour. The native receiver wakes only the gateway. The gateway renews and settles scheduled deliveries through its creator-bound connection, using durable receipts and bounded active-work keepalive.

Foundry

AIServices S0, local auth disabled

Project autopilots-project with deployment gpt-6-1-sol (model gpt-6.1-sol, GlobalStandard, capacity 100) in Sweden Central. The runtime managed identity has Cognitive Services OpenAI User. Foundry also holds the external-agent registration and an Application Insights connection.

Container Registry

Runtime dependency base only

Basic registry with admin disabled. It holds the pinned Hermes dependency image, compiled Office tools, and required runtime packages. Only runtime conversion needs AcrPull. Gateway and MCP source changes use public-image releases and never need a custom image build.

Azure Monitor

Log Analytics + Application Insights

Both have local authentication disabled. Gateway and runtime managed identities publish metadata-only OpenTelemetry spans with Monitoring Metrics Publisher.

Workload VNet

10.42.0.0/16, North Europe

Holds subnet snet-private-endpoints (10.42.2.0/24) with the private endpoint pe-apmcp-* for the Express environment.

Express managed environment

Public network access disabled

Environment apmcp-* in Sweden Central supplies private ingress for the linked private-MCP Sandbox Group.

Sandbox VNet

10.44.0.0/16, Sweden Central

Subnet snet-sandbox (10.44.0.0/24) is delegated to Microsoft.App/environments. Runtime and gateway Groups attach through VNet connections. Peered in both directions with the workload VNet.

Private DNS zone

privatelink.swedencentral.azurecontainerapps.io

Resolves the private MCP hostname to the private endpoint. Linked to both VNets.

Teams and Microsoft 365 entry points

Reference implementation

Personal messages and explicit Agent User mentions are supported entry points. Delivered replies, selected reactions, Mail notifications, and Office comment events have workload-specific handling.

Shared groups are a shared audience. Private per-person delivery and human on-behalf-of identity are not implemented.

Agent 365 channel and identity binding

Channel identity

Each Worker has an Agent Identity and Agent User. Agent 365 binds its endpoint and permissions, then delivers Microsoft 365 activities to /api/messages. The Agents SDK authenticates incoming requests.

Gateway Sandbox

Memory suspend / immediate native Runs

Authenticated Teams activities use the direct bridge-to-runtime path. The gateway does not persist interactive payloads or create recovery references. The journal retains schedule receipts and bounded conversation state with a checked Blob backup. Model inference and tool calls remain in the runtime.

Agent runtime

ACA Sandbox / native Runs

Deployment owns compute. The runtime owns execution of native Runs. Active-only keepalive protects work. Memory resume preserves processes; source releases preserve the Sandbox ID and URL. Native home archives recover runtime state, while the independent gateway journal preserves scheduling receipts and bounded conversation state.

Customer VNet

Workload connectivity

Gateway and runtime attach here. Private endpoints connect managed services; private MCP ingress joins the same network boundary. Peering reaches the enterprise hub. Routes and DNS provide reachability; identity still controls access.

Service Bus private endpoint

Target design / receiver routing must be verified

Private endpoint and DNS can connect workload clients to Premium. A managed receiver runs outside the actor, so actor VNet attachment alone does not establish receiver reachability. Verify the supported native connector network path before disabling public broker access. Entra authorization remains required.

Foundry private endpoint

Target design

The Foundry private endpoint connects model access to the workload VNet. Private DNS resolves the model endpoint to its private address; the runtime still authenticates with its managed identity.

Custom MCP

Optional adapter

Add an ACA-hosted adapter when a backend lacks MCP. It exposes a private MCP interface and reaches backend APIs through the workload VNet and enterprise hub. Use a supported private-ingress hosting configuration.

Service Bus queue and dead-letter handling

Target: private broker plus verified receiver route

The single per-Worker queue carries scheduled metadata only; it is not an activity-recovery or request/reply transport. Native receivers own PeekLock; the gateway renews and settles through its own connection. A private endpoint is not proof of receiver reachability. Source polling affects scheduled work only. Unknown effects stop, and DLQ is visible failure state, never successful delivery.

Foundry model inference

Target design: private endpoint

The agent runtime calls Foundry through the private endpoint. Runtime managed identity and RBAC authorize inference; private routing and DNS provide reachability. The model service remains outside the workload subnet.

Enterprise hub

Shared network services

VNet peering connects the workload spoke to hub routing, DNS, and firewall services. The hub provides controlled public egress and private routes to existing customer services, including MCP endpoints.

Microsoft-hosted MCP tools

Public HTTPS

Use approved Microsoft-hosted tools, such as Azure DevOps and Microsoft 365 MCP integrations. Configure permissions for each service. Microsoft 365 operations use the approved Agent User flow; other services require their own supported connection.

Existing private MCP

Customer-provided service

Connect to an MCP server already running in the customer network through private routing and DNS. Reuse its approved authentication and permissions; no new MCP host is needed in this solution.

Backend systems

Customer APIs

Custom MCP reaches these APIs through the workload VNet, peering, and enterprise hub into the private customer network. Backends keep their existing interfaces and permissions; they do not need to implement MCP.
