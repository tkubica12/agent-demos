Porovnáváme dva směry sbližování: framework rozšířený o harness a hotový harness použitý jako součást aplikace. Oba musí projít stejnou hranicí schopností, důkazů a publikace.

Explorace není pevný workflow

Agent zvolí dotazy, prohlédne nalezené pasáže, hledá protiargument a opraví draft. Dopředu neznáme konkrétní zdroje ani potřebná navazující ověření.

Publikace není agentská improvizace

Host přijímá jen strukturovaný brief. Ověří zdroje, doslovné citace, různorodost a délku; bezpečně vykreslí šablonu a přes Chromium vytvoří PDF.

Stejný model, reálné služby

Všechny varianty používají gpt-6-1-sol v existujícím Foundry přes Entra a stejný WebIQ MCP. Zadání jsou hypotetická; dotazy, odpovědi a artefakty jsou skutečné.

Důvěra má omezený význam

Validní citace není automaticky správný závěr. WebIQ účet vrací indexované pasáže, ne plné stránky. Aplikace nevykonává doporučené nasazení ani obchodní rozhodnutí.

search_web → inspect_source → save_draft → validate_report → publish_report. Šipky popisují obvyklý průchod, nikoli ručně napsanou agentskou smyčku. Další dotaz i opravu volí příslušný nativní harness. WebIQ klíč zůstává v procesu hosta; model jej nedostává.

Nejvýše 6 hledání, 5 různých čtených zdrojů, 18 společných tool calls a 360 sekund. Modelový limit je 24; Deep jej kontroluje callbackem, MAF limitem iterací a Node runtimes po assistant response. Nejde o totožný pre-request mechanismus. Nativní TODO není společný aplikační tool call. Shell ani agentem dodané HTML nebo výstupní cesty nejsou přípustné.

Trvale uložený SQLite ledger hlídá 240 operací, odhad 200 USD a 10 000 WebIQ volání. Neúspěch s neúplnou usage ponechá rezervu 3,25 USD. Read-only WebIQ HTTP 429/502/503/504 má jediný zaznamenaný retry; případné opakované search volání se znovu účtuje.
