Scope and structure

The showcase is a working support-desk agent in a live Foundry project. Every screen here is that project. Every score, trace and alert is a real run.

The tour runs capability first, so the platform's range is established. Then one agent, taken apart. Then the discipline that keeps the agent honest, which is where Foundry separates itself from a model endpoint with a UI.

  • Six sections, about an hour with questions.
  • Every screen is the same project and the same agent.
  • Nothing is staged, and the numbers move between runs.

Verdict

Those four cover the claim end to end: every model behind one contract, one agent definition, complete visibility, measured improvement.

The account owns model deployments, quota and keys. The project owns agents, knowledge, memory, traces and evaluations. One account carries many projects, which is how teams share quota without sharing agents.

The home page carries the project endpoint and the field that reads API key authentication is disabled for this project. Microsoft Entra is the only way in.

Models and services

OpenAI, Microsoft, DeepSeek, Mistral and MoonshotAI, deployed side by side in one project. Selecting Kimi-K2.6 shows the same project endpoint, the same disabled-key notice, and a Python sample built on the OpenAI client with an Entra token provider.

Switching vendor is switching one string. The endpoint, the authentication and the client stay where they are.

The Deployment type column answers a compliance question, not a performance one. Global Standard draws on Microsoft's global capacity. Data Zone Standard keeps inference inside a geography. Provisioned buys dedicated throughput, and the PTU Calculator button sizes it.

In this project Mistral-Large-3 runs on Data Zone Standard and everything else on Global Standard, so the contrast is visible without leaving the page.

Batch jobs sits next to Deployed models. Batch runs asynchronously against a separate quota pool at a lower price, which is the right answer for backfills, bulk classification and offline evaluation.

Managed compute deployments is the toggle above the list. Serverless is per-token on shared capacity; managed compute puts an open-weights model on dedicated GPUs you can size, which is where a model you brought yourself would land.

One completed job: a supervised fine-tune of qwen3-32b. It earns its cost in two cases. Style and format that prompting cannot hold. A smaller model that has to behave like a larger one. Little else.

Rule

Reach for instructions, then skills, then knowledge, then the optimizer. Fine-tune when those four have run out.

Speech, translation, language and content understanding, each with its own playground. Three of the fifteen are PII redaction alone: text, document and conversational. Wiring a language model to redact PII or extract document layout is slower, less accurate and more expensive than the service that already does it.

The Customizations tab holds a custom neural voice or a trained extraction schema, for the cases where the stock service is close but not exact.

The agents

Prompt agents are configuration: a model, instructions, attachments, no code. Hosted agents are your code on Foundry's runtime. External agents run wherever you like — this one is on Azure Container Apps — and register back, so traces, evaluations and monitoring still work.

Verdict

An agent does not have to run on Foundry to be governed by Foundry.

A routine is a schedule, a prompt and an agent. No external scheduler, no function app, no cron container. daily-support-quality-review runs weekdays at 09:00 and last ran two hours before this screenshot; case-follow-up-reminder is paused, so both ends of the lifecycle are on one page.

Model, voice mode, instructions, tools, knowledge, memory, guardrail. The left rail is the entire conceptual model of a Foundry agent, and it is the same list whether the agent is built here or in code. The rest of the tour fills in each row.

Improve instructions rewrites the system prompt with a model, in seconds, against the agent's current configuration.

Yes. The YAML tab on the right shows the definition the SDK posts, and Call agent hands back the client snippet. The portal is a view over the API, not a parallel product.

The main hosted agent takes a support case, decides it needs documented policy, and calls a prompt agent over A2A. Two different agent kinds, one conversation. Filtering the trace to a2a reduces thirty-nine spans to the three that carry the delegation.

What you attach to an agent

Six tools, three kinds: Azure AI Search, Agent2agent and Model Context Protocol. Registering an MCP server publishes its tools to every agent in the project. Registering an A2A agent makes another agent look like a tool. Same list, same permissions, same audit trail.

A toolbox groups tools behind a search interface, so the agent receives a short relevant list instead of a hundred schemas pinned into its system prompt. Get code returns a single MCP endpoint fronting the whole box, versioned — the support toolbox here is on version 3.

Three markdown skills: when to escalate, when a user-profile fact may be stored, and how a support reply should read. Upload a .md or a .zip to register one. The agent calls load_skill at run time, which keeps the system prompt small and lets policy change without a redeploy.

Those load_skill calls appear as spans in the trace later in the tour, and as rewritable surface in the optimizer after that.

A guardrail is a set of rows: a risk type, an intervention point, an action. Indirect prompt injections, blocked. A content-safety threshold beside it. The intervention point column carries the important claim, because the same policy can apply where the agent reads a tool result — which is exactly where indirect injection arrives.

Blocklists for exact terms, and an Integrations tab in preview for third-party filters.

Microsoft.DefaultV2 is applied to the gpt-5.4 family without anyone asking, so a project is never unprotected by accident.

Try in playground runs a prompt against the guardrail alone and shows the block firing.

One knowledge base, two sources: an Azure AI Search index of documents and a web source, both active. No chunking script, no embedding pipeline, no retrieval orchestration inside the agent.

A chat model and a retrieval reasoning effort turn one question into a plan of several queries. Retrieval instructions then route between sources in plain English: internal documents for operations and procedures, web only for current public information, cite sources. Agentic retrieval, written as a paragraph.

Add sources and Upload files handle ingestion. Verbalization turns images and diagrams into searchable text, so a figure inside a PDF stops being invisible.

Web sources carry a Grounding with Bing notice stating that customer data flows outside the Azure compliance and geo boundary. That constraint decides whether a web source belongs in a regulated workload.

Three features: chat summary, procedural memory and user profile. They are fixed when the store is created and cannot be changed afterwards, so the shape of what an agent remembers is a provisioning decision. The default time-to-live of 2,592,000 seconds is thirty days.

Warning

The user-profile prompt in this store excludes credentials, financials, precise location and critical PII. Memory without that instruction is a data-protection incident waiting to happen.

The improvement loop

Duration, tokens in and out, estimated cost, evaluator scores and the agent version, per run, filterable by all of them. Two controls matter more than the table: Annotate on every row, and Create dataset in the corner.

The managed-identity token fetch, the POST to the toolbox MCP endpoint, three load_skill calls, seven model calls, the A2A hop. Everything claimed earlier in the tour appears here as a span with a duration.

The right pane is raw OpenTelemetry — gen_ai.agent.id, gen_ai.operation.name — so the same data lands in whatever you already run.

Annotations reach a trace three ways: from the end-user application through the feedback API, from a reviewer working the trace list after the fact, and from automatic evaluators that already scored the run. Filter to the bad ones, press Create dataset, and yesterday's failures become tomorrow's evaluation set.

  1. RunTraced without being asked.
  2. AnnotationUser, reviewer or evaluator.
  3. DatasetBuilt by filtering, not by hand.
  4. EvaluationThe opinion becomes a number.
  5. OptimizerThe number moves the agent.

Rule

Never write an evaluation set by hand while a trace list is sitting there full of real failures.

The list mixes built-in evaluators, a rubric-based custom evaluator, and scheduled quality runs. One row reads Continuous Eval Run with a rule name attached: that is production traffic being sampled and scored on a schedule, with nobody starting a run.

Continuous evaluation samples responses the evaluation service can read back. Prompt agents invoked through the project Responses API qualify. Hosted agents called through their own endpoint produce session-scoped ids, and the sampled run fails with session_not_accessible.

A rule also takes several minutes to activate. Responses emitted immediately after it is created are never sampled, and runs appear roughly six minutes after the response.

Eleven runs on the third tab. The AI red teaming agent generates attack prompts across risk categories and reports issues found per run. The jailbreak attempts blocked in the Operate alerts, one chapter later, are exactly what red teaming is built to provoke.

Give it an agent, a dataset and an evaluator. It proposes candidate configurations, scores each one against the dataset, and ranks them. It changes two surfaces: the system prompt and the skills.

Skills are not documentation. They are editable surface the optimizer is allowed to rewrite, which is why they were worth registering earlier.

Four candidates against a baseline of 0.591. Two rewrote skills, two rewrote the system prompt, and two of the four made the agent worse. The winner reached 0.637 in 54 minutes. Every row links to the evaluation run behind its score, and Deploy best candidate promotes it.

Enterprise readiness

Overview, Assets, Compliance, Quota, Admin — scoped to a subscription across every project, not to one agent. Running agents, estimated cost, success rate, token usage and security alerts on one page.

Two MEDIUM alerts here read A Jailbreak attempt on your Azure AI model deployment was blocked by Prompt Shields, each with a Review action. The guardrails from earlier in the tour, surfaced as security findings rather than as configuration.

The button takes an agent that is not running on Foundry and brings it under the same inventory, policy and alerting as the agents Foundry hosts. Existing agents on other platforms join the estate without being rebuilt.

A protocol (A2A or MCP), the agent's URL, the agent card URL, and the OpenTelemetry agent id that ties incoming traces to the registered asset. For this showcase every value comes from the external-agent deployment output.

Registration is a portal step. There is no script for it in this repository.

Open AI Gateway and select fshow-aigw-si4ons in Sweden Central. Show one published model, showcase-chat, and Microsoft Learn MCP. The model backend and native telemetry use the gateway's managed identity.

The hosted agents still call Foundry directly. Memory, Toolbox, A2A and approved case writes are unchanged. Inbound gateway runtime access still needs a key; the operator CLI retrieves it into memory through Entra-authenticated ARM.

From the repository root, with the main-agent environment prepared and Azure CLI signed in:

Set-Location foundry-showcase
uv run --project main-agent --no-sync python scripts\ai_gateway.py
uv run --project main-agent --no-sync python scripts\ai_gateway.py budget-demo --approve
uv run --project main-agent --no-sync python scripts\ai_gateway.py telemetry

The isolated fshow-aigw-models-si4ons account contains one low-capacity GPT-5.4-mini deployment. No shared-account deployments or case-write tools are published. The gateway-wide key is neither printed nor persisted; this is an administrative demo, not secretless application integration.

Terraform manages publication, policies, MCP, and native OTLP. Native first creation followed by Terraform adoption is verified; a full from-empty gateway bootstrap is not. See the operating commands and architecture decision.

No general retirement of conventional APIM AI functionality was established. Do not present the new tier as proof of that claim or of native Foundry feature compatibility.

  • Model requests succeed, then a bounded burst returns rate-limit 429. A tiny per-key Chat Completions budget returns 403.
  • Learn search works. Blocked fetch returns HTTP 200 with MCP isError; unpublished code search returns 404.
  • Native monitoring shows policy and tool spans, logs, and actual token and estimated-cost metric samples. Payload capture is off.

Model policies are 5 requests/minute, 5,000 tokens/minute, and $0.05/calendar day per runtime key. Rate enforcement is approximate. The token policy appears in real spans, but its threshold rejection has not been separately tested.

The budget command temporarily overrides only its disposable key to $0.000001, makes at most four Chat Completions calls, restores its override, and revokes the key. Delayed accounting can overshoot the limit. Responses transport works; equivalent cost-budget enforcement is not yet established. Neither these estimates nor the low model capacity are hard Azure spending caps.

Fetch stays in the published tool list but returns gateway denial code ToolNotAvailable. Check MCP semantics, not just HTTP success. Code search is excluded from the published list and its direct call is rejected with HTTP 404.

Copy the run's trace ID into telemetry --trace-id <32-hex-id>. Logs and spans correlate to that run; token/cost metrics remain gateway-wide recent sample aggregates, not trace totals or an Azure bill. Allow ingestion delay and run probes serially; a previous rate window can require a 61-second cooldown.

Current public capabilities: native OTLP and cost budgets, then per-key overrides and MCP selection/blocking.

Private endpoints and VNet injection, customer-managed keys, and bring-your-own storage and search are configured on the account in the Azure portal, not in the project. An agent inherits them; it does not choose them.

Note

The Foundry account behind this showcase is shared and not network-isolated. The VNet and private endpoint in the showcase's own Terraform protect its container apps and storage, not the Foundry account.

A Foundry agent is reachable over the Responses API, over A2A and over MCP with no extra work — that covers most integrations by itself. Beyond it, the Microsoft 365 Agents Toolkit publishes to Teams and Microsoft 365 Copilot, and Agent 365 governs agent identities across the tenant.

Everything earlier in the tour — the guardrails, the traces, the evaluations, the optimizer — stays attached to the agent through all of those surfaces.

Foundry's argument is not that it can run an agent. It is that it can tell you, in a number with a trace behind it, whether the agent got better.
