Hosted agent identity, isolation, and scaling

Four identifiers decide which micro-VM a request lands on, which user it counts as, and which conversation it continues. This explains what each one does, what a middle tier should send in three different deployment shapes, and what a live agent actually did under load.

The model

The platform runs one instance of your container per agent_session_id. Send the same string twice and both requests land on the same running instance: same processes, same memory, same disk. Send a different string and you get a different instance, isolated from the first at the virtual machine boundary.

You invent that string. The platform does not hand you a session ID to store; your middle tier chooses one on every call. A session appears the first time you name it and is deprovisioned after 15 minutes with no traffic.

Every question about isolation, concurrency and cost reduces to one decision: which strings does the middle tier choose?

Container protocol 2.0.0, through the Responses API, carries it in the request body:

middle tier, Responses

response = responses_client.create(
    input=user_message,
    extra_body={"agent_session_id": session_id},
    extra_headers={"x-ms-user-identity": user_id},
)

Container protocol 1.0.0, through the Invocations endpoint, carries it as a query parameter. This is the only binding the Invocations path honours, which the load lab in this repository relies on:

middle tier, Invocations

POST .../endpoint/protocols/invocations?api-version=v1&agent_session_id=pool-0

This is the point where mental models usually go wrong. x-ms-user-identity looks like a routing key because it identifies a person, and people map to replicas in most systems. It does not route anything here.

Rule

The session ID is a capacity decision. The user identity is a security decision. Change the session ID to spread load; never change the user identity for the same reason.

Sending x-ms-user-identity requires the data action Microsoft.CognitiveServices/accounts/AIServices/agents/endpoints/UserIdentityImpersonation/action. No built-in role grants it, including Foundry Owner. Without it the call fails with 403.

Once the caller holds that permission, the value itself is not validated against a directory. Microsoft's own multiplexing sample hardcodes two plain labels:

foundry-samples · invoke_previous_response_isolation.py

user_a="alice",
user_b="bob",
...
"extra_headers": {"x-ms-user-identity": user_id},

So an arbitrary GUID would work. The trust boundary is the calling service, proven by role assignment; the platform then treats whatever that service asserts as the truth and re-emits it to your container.

Sending the header from an account holding Owner at management-group scope still fails, which confirms the permission is genuinely separate from ownership:

The four identifiers

LevelIdentifierQuestion it answersWho chooses the value
Agentazure.yaml name and versionWhich code and which model?You, at deploy time
Sessionagent_session_idWhich micro-VM?Your middle tier, per request
Userx-ms-user-identity in, x-agent-user-id outWhose data is this?Your middle tier, from a validated token
Conversationprevious_response_idWhich thread continues?The platform mints it; you store and replay it

Naming a session that does not exist creates it. Naming one that exists routes to it. Naming one whose compute was deprovisioned after idling resumes it with the disk intact.

That makes the session name a pure function of your routing policy: user-<oid> for per-user isolation, shared for full multiplexing, pool-7 for bucketing. The middle tier can recompute it rather than persist it, as long as the function is deterministic.

Sessions can also be listed, inspected and stopped through a REST collection under the agent endpoint, or with azd ai agent sessions.

Warning

The accepted character set is undocumented and stricter than it looks. sess_abc123, GUIDs and lab-run1-user3 are accepted; probe-a and probea both returned 400 invalid_session_id in testing on 3 August 2026. Validate your naming function against the live endpoint before relying on it.

If the container read a header the caller could set, any caller could read any user's data. Splitting the two lets the platform validate, resolve, then inject — so get_request_context().user_id is always platform-asserted.

With no delegation the platform derives the value from the caller's Entra token. Probing the showcase agent returned an x-agent-user-id exactly equal to the signed-in account's Entra object ID, so one caller then means one user regardless of how many people sit behind your front end.

The header constants in azure-ai-agentserver-core define the contract more precisely than any documentation page:

azure/ai/agentserver/core/_platform_headers.py

USER_ID: str = "x-agent-user-id"
"""The platform-injected global, cross-agent partition key for
per-user state. The same user yields the same value regardless of
which agent they interact with. Use it as the primary partition key
for per-user data (profiles, preferences, OAuth tokens, memory)."""

Protocol 2.0.0 adds x-agent-foundry-call-id, an opaque per-request token the container must forward verbatim on outbound calls to Foundry services such as Storage, the Toolbox MCP proxy, and A2A. The user ID is deliberately not forwarded: first-party services do not trust it. The call ID is the capability; the user ID is only a partition key.

Note

Whether a delegated x-agent-user-id is the literal string you sent or a canonicalised form of it is untested here, because the 403 blocked the experiment. It is stable per user either way, which is all a partition key needs.

Each call returns a response with an id. Passing that id as previous_response_id on the next call continues the thread. Store the latest ID per thread in your own database; that is the whole mechanism. The agent server SDK has no conversation object.

The platform ties every chain to the user who created it. If Bob sends Alice's previous_response_id while sitting in the same session, the call fails. Inside the container, context.get_history() returns only what the current request's user is authorised to see.

Verdict

This is the one piece of multi-user isolation you get for free in a shared session, and it is the piece people worry about most. Everything else your container touches is your problem.

Three middle-tier recipes

middle tier

oid = validated_token["oid"]              # stable, immutable

session_id = f"user{oid.replace('-', '')}"
user_id    = oid

Use the subject claim your identity provider guarantees is immutable: oid for Microsoft Entra, sub for anything else. Never use email or user principal name; a rename would orphan the user's history and disk.

Every user gets a private machine with a private filesystem, isolated at the VM boundary. Nothing in your container code has to be concurrency-safe across users, because no two users share a process.

Verdict

Correct when the sandbox does real work on the user's behalf: running code, holding a workspace, processing untrusted content. Expensive when it only relays prompts to a model.

middle tier

session_id = "shared"                     # one micro-VM for everyone
user_id    = validated_token["oid"]       # still per user

One container instance serves the entire population. Conversation history stays private per user because the platform partitions it. Everything the container writes itself — files, module variables, caches — is shared unless you key it by user.

This shape needs container protocol 2.0.0. On 1.0.0 a session is bound to a single caller identity, and concurrent users on one session interfere with each other.

There is no HTTP scaler and no platform concurrency setting. The pool lives entirely in your middle tier, which is why it can implement exactly the policy you want.

middle tier, sticky fill

def session_for(user_id: str) -> str:
    if user_id in assigned:
        return assigned[user_id]                    # returning user is sticky
    slot = next((s for s, n in counts.items() if n < max_users_per_session), None)
    if slot is None:
        slot = f"pool-{len(counts)}"                # grow only when all are full
        counts[slot] = 0
    assigned[user_id] = slot
    counts[slot] += 1
    return slot

Sticky fill keeps a user's turns on one machine and opens a new session only when every existing one is at capacity. Hash-based assignment is stateless but reshuffles everyone when the pool resizes. Round-robin spreads load but scatters a user's turns.

Two caps do different jobs and should not be conflated. A limit on concurrent in-flight requests per session protects latency. A limit on users per session bounds the blast radius of a container-side bug. Neither is a platform feature; both are variables in your code.

Note

Because users read and type between turns, concurrent requests are a small fraction of the user count. Size the pool against measured peak concurrency, not against registered users.

It is tempting to skip delegation when each user already has a private session. Conversation history would still be private, because the session is private.

Foundry memory is not. The SDK describes x-agent-user-id as a global, cross-agent partition key, and without delegation it resolves to the middle tier's own managed identity for every request. All one thousand users would then read and write a single memory partition.

Rule

Session name and user identity are independent settings. Choose the session name for capacity and isolation; always set the user identity to the real end user.

The two rows keyed by session are the ones that surprise people. They are per machine, not per person.

Two users on different session names get different filesystems, automatically and unconditionally. Two users on the same session name get one filesystem, and the platform does nothing to divide it. Building the drawers is your job:

container

ctx  = get_request_context()
path = Path.home() / ctx.user_id / "MEMORY.md"

The disk outlives idle deprovision. Stopping a session and calling it again returned a new instance ID with a resume counter incremented and the marker file intact, and a resume cost 13.67 s at the median against 42.74 s cold. Sessions expire on a rolling 30-day window measured from last access.

Warning

Thirty idle days deletes the session and its disk. Treat $HOME as a warm working cache and write anything that must survive to Blob storage or a database.

Move a user to a different session and their Foundry memory comes with them, because it is keyed on the user and scoped across agents. Their conversation history does not: history is scoped to the session as well as the user, so a user reassigned to a new bucket starts a fresh thread there.

That asymmetry decides pool design. Sticky assignment matters when threads must survive; if every turn carries its own previous_response_id from your database, reassignment is cheap.

Note

The memory half is documented: the agent server SDK calls x-agent-user-id a global, cross-agent partition key. The history half is inferred from the session-scoped storage model and was not tested here. Replaying a previous_response_id from a different session would settle it.

One session is one Linux process running one Python interpreter with one module namespace. Ten concurrent requests are ten coroutines sharing it. Anything defined at module level is created once at container start and shared by everyone.

The most common instance in LangGraph is a constant thread key:

wrong

graph = builder.compile(checkpointer=InMemorySaver())   # module level

async def handler(request, context, _):
    return await graph.ainvoke(
        {"messages": [...]},
        config={"configurable": {"thread_id": "chat"}},  # same for everyone
    )

Alice and Bob land in one shared conversation. No file is involved; the state is a dictionary in memory. Microsoft Agent Framework has the same shape when a thread is created once at module level and reused by every request.

right

ctx = get_request_context()
config = {"configurable": {"thread_id": f"{ctx.user_id}:{conversation_id}"}}

Per-invocation framework state is safe: LangGraph state passed through ainvoke, a Microsoft Agent Framework run, a local variable. What is unsafe is anything you attach at module scope — a checkpointer with a constant key, a client built with the first caller's token, a global registry reconfigured per request.

The race needs two things: shared state and an await. Between any two awaits another request runs.

the race

_current_profile = None

async def handle(req):
    global _current_profile
    _current_profile = load_profile(req.user_id)
    answer = await model.chat(...)        # control yields here
    return f"{_current_profile}: {answer}"

Alice sets the global, yields, Bob overwrites it, Alice resumes and reads Bob's profile. With one session per user the process only ever serves one person, so a constant key is accidentally correct and the bug stays latent for the entire life of the project.

  • Keep module scope to immutable configuration and clients that carry no user identity.
  • Hold per-request state in locals, or in a contextvars.ContextVar, which is per-task and survives awaits — this is how the SDK implements get_request_context().
  • Include the user ID in every cache key, checkpointer key and file path.
  • Guard read-modify-write on any shared file with an asyncio.Lock.
  • Test with two users interleaved; a single-user test cannot detect any of this.

This repository's own memory_store.py shows the correct shape and the remaining gap: a module-level singleton backed by one sandbox-wide JSON file, whose contents are keyed {"users": {user_id: ...}} so the data model is multiplex-safe, but whose writes are unlocked read-modify-write and whose MEMORY_DEFAULT_USER_ID fallback would collapse users together if the real user ID were not threaded through.

The idle window dominates. Twelve sessions each holding 15 minutes after a 15-second burst is almost entirely wasted capacity, and it scales linearly with user count.

A session can be stopped explicitly instead of waiting out the idle timeout. Doing so at the end of a burst took the same workload from 31.4 to 1.4 sandbox-minutes.

Verdict

If your middle tier knows when a user's work finishes, per-user isolation plus explicit stop beats pooling: near-identical cost, with a real VM boundary between users.

A thousand concurrent users on one session each is not a budget problem before it is an address-space problem. That constraint alone forces either pooling or aggressive stopping.

Choosing a shape

The deciding question is not user count. It is whether the container touches anything on the user's behalf.

Isolate The container executes code, holds a workspace, or handles untrusted content, so a VM boundary is doing real security work.
Multiplex The container assembles a prompt, calls remote tools, and reads a database, so the only state that matters is already partitioned.
Pool You want a blast-radius cap without paying per user, and you can carry a user-to-session map in the middle tier.

An agent built on remote tools alone multiplexes safely once its own state is keyed by user. A harness with local tools that writes files, runs shells, or clones repositories should get a machine per user.

If the answer is one shared session for a thousand users, you are describing interchangeable stateless replicas. Azure Container Apps expresses that declaratively with concurrent-request scaling and replica bounds, and no routing code in your middle tier.

What hosted agents add is per-session durable compute: a named machine with a private filesystem that scales to zero and resumes with its state. Immutable versions, instant rollback, version-scoped evaluation targets, a sessions API and a per-agent Entra identity come with it. Registering an external agent gives a Container Apps deployment Foundry tracing and trace-based evaluation, but external agents are versionless, so lifecycle management does not carry over.

Note

Hosted agents appear to run on Azure Container Apps Sandboxes rather than dynamic sessions: probes report a host name of adc-sandbox, and the tier S shape of 0.5 core, 1 GB and 20 GB disk matches this agent's configuration exactly. This is inference from observed behaviour on 3 August 2026, not documented.

The session name is a capacity decision and the user identity is a security decision; almost every mistake in this area comes from letting one of them do the other's job.
